# DiceFive: internationalisation (i18n) and localisation (l10n)

The plan for moving every player-visible and spoken string out of Kotlin and into string
resources (i18n), so that adding a language later (l10n) is a matter of adding one file per
language. **No other language is planned yet.** Every step up to and including Step 4 is
mechanical, ships English only, and **must change nothing a player sees or hears.**

This file is written so that an agent new to the project can pick up the next step on its own.
Read "Picking up a step" first, then the step itself.

### How to move a string (the worked example)

Before (`LeaveGameConfirmation.kt`):

```kotlin
DiceFiveDialog(
    title = "Leave game?",
    ...
)
```

After - the string in `strings.xml`, under a comment naming the screen:

```xml
<!-- Leave game confirmation (ui/game/LeaveGameConfirmation.kt) -->
<string name="game_leave_title">Leave game?</string>
```

and in Kotlin:

```kotlin
import net.zodac.dicefive.resources.Res
import net.zodac.dicefive.resources.game_leave_title
import org.jetbrains.compose.resources.stringResource

DiceFiveDialog(
    title = stringResource(Res.string.game_leave_title),
    ...
)
```

Each key needs its own import (`net.zodac.dicefive.resources.<key>`). The `Res` accessors are
generated by the build, so a new key shows up as unresolved until Gradle compiles once.

With an argument: `<string name="game_standing_spoken">%1$s place</string>` and
`stringResource(Res.string.game_standing_spoken, ordinal(place))`.

A plural (see "Plurals" below): `pluralStringResource(Res.plurals.game_cup_cd, rolls, rolls)`.

Inside a non-composable lambda (`semantics { }`, `clearAndSetSemantics { }`, an `onClick`),
resolve first and use the `val`:

```kotlin
val rollLabel = stringResource(Res.string.game_cup_roll_action)
val cupDescription = cup?.let { pluralStringResource(Res.plurals.game_cup_cd, it.rollsRemaining, it.rollsRemaining) }
Box(
    modifier = Modifier.clearAndSetSemantics {
        contentDescription = cupDescription.orEmpty()
        onClick(label = rollLabel) { ... }
    },
)
```

### Verify (all of it, every time)

From `/work`:

```sh

# here anyway (allWarningsAsErrors, lint warningsAsErrors).
./gradlew -q :app:shared:testAndroidHostTest :app:android:testDebugUnitTest \
  :app:shared:lint :app:android:lintDebug \
  :app:shared:compileKotlinIosSimulatorArm64 :app:shared:compileTestKotlinIosSimulatorArm64 \

```

While iterating, a single Robolectric class: `./gradlew -q :app:android:testDebugUnitTest --tests '*BoardSemanticsTest'`.
Failures are in `app/android/build/test-results/testDebugUnitTest/TEST-*.xml` (grep for `<failure`).

Then:

- **Word for word.** For every string moved, the old literal and the new resource text are
  identical, including punctuation and spacing (`git diff` - the removed Kotlin literal and the added
  XML line should read the same).
- **Tests that assert on the text still pass unchanged.** If a test asserted on English text and
  still passes, the move was right. Never edit a test's expected English to make it pass - that
  means the text changed.
- **Spoken text has a test.** If a moved spoken string (a `contentDescription`, `stateDescription`,
  action label, announcement) isn't asserted word for word anywhere, add a Robolectric assertion
  for it (Step 0 did this for the cup in `GameScreenCupGateTest`).
- **Build the APK and send it** (`app/android/build/outputs/apk/debug/`), per `CLAUDE.md`, saying
  what to check by hand - including what TalkBack should say, since it hasn't been heard on a device.

## Where things stood before Step 0

- **No string resources existed.** The only one was `app_name` in
  `app/android/src/main/res/values/strings.xml` (the launcher label, which stays there). Every other
  string was a Kotlin literal: roughly 900-1,100 of them across the 183 files in `app/shared`.
  - About 85% were in `ui/`. `RulesScreen.kt` alone had about 120 prose lines; Setup, Settings,
    Styles and Statistics had 20-40 each.
  - The rest was display text held by the model, game and data layers: `GameMode.displayName`,
    `AchievementCategory.label`, the titles and descriptions of the ~87 achievements, the score
    category names, the modifier and difficulty names, `Standing.label()` / `spoken()`
    (`game/Standings.kt`, moved in Step 0), and the banner text in `data/achievements` ("New
    Personal Best").
- **The resource system was already in place.** Compose Multiplatform resources were already used
  for drawables and fonts (`composeResources/`, with `Res` in `net.zodac.dicefive.resources`). The
  same system handles `<string>`, `<plurals>` and `<string-array>`, with `values-xx/` locale folders,
  from one set of files, on both Android and iOS. No new library is needed.
- **Nothing saved holds display text.** The Leaderboard stores `gameModeId`; achievements are
  stored by id. Moving text into resources needs no Room or JSON migration.
- **English grammar was built into the code in about 15 places:**
  - About 10 hand-rolled plurals (`if (n == 1) "roll" else "rolls"`): `DiceCupPanel` (done in Step
    0), `GameScreen`'s timer, `StylesScreen`'s unlock counts, `LicensesDialog`'s `ComponentKind`,
    `AchievementAnnouncements`, `RulesScreen`'s "is/are locked".
  - English ordinals in `Standings.ordinal` (done in Step 0).
  - `grouped()` (`ui/common/Formatting.kt`) hard-codes `,` as the thousands separator.
  - `spokenList()` (`RulesScreen.kt`) joins with ", " and " and ".
  - Sentences assembled from pieces, e.g. `targetProgress` and `stackedSpokenState` in
    `ScoreGrid.kt` (`"$rolled of $n rolled, $inPlace in place"`, a `listOfNotNull(...)` joined with
    ", " and then capitalised). Word order can't be translated when a sentence is built like that.
- **Dates were already localised:** `formatTimestamp` uses each platform's own date APIs.

## Decisions

### Plurals: externalised in `<plurals>`, using Compose resources' own CLDR rules

Three options were weighed:

| Option | Verdict |
|---|---|
| Roll our own `plural(locale, n)` function | **No.** Plural rules are CLDR data, not logic worth owning: Russian, Polish and Arabic have 3-6 categories, and "one" in Russian also covers 21, 31, 101... Every new language would mean new hand-written rules and tests. |
| A library (e.g. an ICU port, or a KMP i18n library such as moko-resources or Lyricist) | **No.** It would duplicate what's already bundled, add classes to the APK (the project already turned down kotlinx-datetime for ~180 classes - see `formatTimestamp`), and moko/Lyricist would replace the resource system rather than extend it. |
| **`<plurals>` in `strings.xml`, read with `pluralStringResource` / `getPluralString`** | **Yes.** `components-resources` 1.12 ships the CLDR plural rule tables in its own `commonMain` (`org.jetbrains.compose.resources.plural.PluralRuleLists`, indexed by locale), so plural selection is the same on Android and iOS, and needs no platform code. A translator supplies the forms their language needs, in the same file as every other string. |

How plurals are written (the real one, from Step 0):

```xml
<plurals name="game_cup_cd">
    <item quantity="one">Dice cup, %1$d roll left</item>
    <item quantity="other">Dice cup, %1$d rolls left</item>
</plurals>
```

```kotlin
pluralStringResource(Res.plurals.game_cup_cd, rolls, rolls)
```

Rules for plurals:

- **The whole phrase goes in the plural, not just the noun.** "%1$d rolls left" is one plural;
  never `"$n " + plural(noun)`. Other languages inflect the verb and adjectives too.
- **Always include the number (`%1$d`) in every form, including `one`.** In some languages `one`
  covers 21, 31 and so on, so "a roll" or a hard-coded "1" would be wrong there.
- **The count is passed twice:** once to choose the form, once as the format argument.
- **Zero is not a plural form.** English has no `zero` category in CLDR, so "None" or "No
  achievements" is a separate `<string>`, chosen in code with an explicit `if (n == 0)`.
- **A plural that only changes a verb is still a plural**, e.g. "The %1$s is locked in chains" /
  "The %1$s are locked in chains".

### Ordinals and number formatting: each platform's formatter, behind `expect`/`actual`

CLDR plural tables in Compose resources are **cardinal only** - they can't produce "1st / 2nd /
3rd". Ordinals, thousands separators and spoken lists go through each platform's formatter, the way
`formatTimestamp` already does:

| Helper | Android (minSdk 26) | iOS |
|---|---|---|
| `ordinal(n)` / `formatOrdinal` (done, `ui/common/Formatting.kt`) | `android.icu.text.MessageFormat("{0,ordinal}")` - ICU's `RuleBasedNumberFormat` would be the direct route but isn't in the public SDK | `NSNumberFormatter` with `NSNumberFormatterOrdinalStyle` |
| `Int.grouped()` (Step 3) | `java.text.NumberFormat.getIntegerInstance(locale)` | `NSNumberFormatter` with `NSNumberFormatterDecimalStyle` |
| `spokenList(items)` (Step 3) | `android.icu.text.ListFormatter.getInstance(locale)` | `NSListFormatter` |

The surrounding words ("tied", "place") go into string templates (`"tied %1$s place"`), not
into the helper.

**These formatters use the strings' language, not the device's.** `values/strings.xml` holds
`common_locale` (`en-GB`), and each translation sets its own. The composable `ordinal()` reads it and
passes it to `formatOrdinal(number, languageTag)`, the `expect`/`actual` function. Without this, a
French phone would get English text (no French file to resolve to) with "1er" in among it.
`BoardSemanticsTest` runs the player tabs under `@Config(qualifiers = "fr")` to check this. Step 3
gives `grouped()` and `spokenList` the same shape: a composable that reads `common_locale`, over an
`expect fun formatX(..., languageTag: String)`.

**Dates follow it too** (`timestamp()` over `formatTimestamp(epochMillis, pattern, languageTag)`): the pattern is a string,
`common_timestamp_pattern`, so a translator can reorder it; the month names are the strings' language's, except that a
device already in that language keeps its own regional form ("Sep" on an en-US phone, "Sept" on en-GB); and the digits are
the strings' numerals.

### Layout direction and plural forms follow the strings' language too

`StringsLanguage` (`ui/common/StringsLanguage.kt`), applied by `DiceFiveTheme` so the app, previews and tests all get it,
makes the two things that otherwise follow the **device's** language follow the strings':

- **Layout direction.** `android:supportsRtl` is on, and Compose takes its direction from the device. Before this, an
  Arabic, Persian or Hebrew phone - which gets English - mirrored the whole app (back arrow on the right, player tabs and
  scorecard columns reversed) and set English paragraphs right to left, moving their punctuation and numbers ("1 of 11"
  drawn as "of 11 1"). `LocalLayoutDirection` is now the direction of `common_locale` (`isRightToLeft`, from each
  platform). The exception is the
  Licences list: licence texts are English whatever the app's language, so both versions of it (Android's views and the
  Compose one iOS draws) are always left to right, with each paragraph reading in its own direction by its first letter
  (so a translated label like "Used by..." still reads its own way). `LicensesDialogTest` checks both in a right-to-left app.
- **Plural forms.** Compose resources picks a form by the platform's current language (`Locale.current`, which on
  Android is `LocaleList.getDefault()`), not by the language the strings came from. A Russian phone ("one" is 21, 31...)
  read English "21 solo games" as "21 solo game", and a Persian, French or Hindi one ("one" includes 0) "0 roll". Its
  own environment is internal API, so `alignPlatformLanguage` puts the strings' language first in the process's
  `LocaleList` when the device's first language is a different one (a device already in it is left alone), on each
  composition of `StringsLanguage`, since Android resets it when the device's language changes.
- **Android's own text.** Some text comes from Android's resources, not the app's: Material's built-in labels and state
  descriptions, and the system's copy-and-paste menu. `MainActivity.attachBaseContext` applies
  `stringsLanguageConfiguration()` (`androidMain`), which runs the whole Activity in the strings' language when the device's
  first language isn't one the app has, so those are English (and the window left to right) too.
  `MainActivityLanguageTest` covers it.

**The rule: no partial translations.** The app is either wholly in a language it has a `values-xx` for (text, plurals,
numbers, dates, direction and Android's own text), or wholly in English, left to right. Only the device's first language
counts, as Compose resources only looks at that one: an Arabic phone whose second language is Spanish gets English. A device
already in the strings' language (en-US for en-GB, es-MX for es-ES) keeps its own regional date forms, which is still that
language. Not covered: which voice TalkBack reads the English with is its own setting.

**iOS, still to do:** Compose on iOS reads the language from `NSLocale.preferredLanguages`, the device's own list, so an
iPhone in a language with no translation would pick the English plural forms by that language's rules. Its
`alignPlatformLanguage` is a no-op for now; fix and check it with the iOS app (Phase 5), on a Mac. Direction and dates
already follow the strings there.

`StringsLanguageTest` covers both (under `ar`, `fa`, `iw` and `ru`), and was checked to fail with the fix removed.

### Text written the other way

A text argument whose first letter is in the other direction from the strings - a player's name typed in Arabic in an English
sentence, or the game's "5x" or a default "Player 1" in a right-to-left one - is wrapped in FIRST STRONG ISOLATE / POP
DIRECTIONAL ISOLATE (U+2068 / U+2069) by `fill()` in `ui/common/Strings.kt`, so a number or punctuation beside it stays where
the sentence put it instead of joining its run. Text in the sentence's own direction is untouched (so English text and tests
are unchanged), and screen readers skip the marks. Text written inside a translation (a mark typed into an Arabic sentence) is
the translator's to isolate, with the same two characters. Covered by `BidiIsolationTest` and `StringsLanguageTest`.

### Other decisions

- **Base locale is British English.** The copy uses British spelling ("colour", "licence"), so
  the default `values/` should be declared as `en-GB` when the platform plumbing lands in Step 5.
- **These stay in code and are never translated:** the game's marks ("3x", "4x", "5x", "2+2",
  "Alibi"); the easter eggs that are triggered by English names (`IrishEasterEgg`,
  `SolutionEasterEgg`); the CPU name generator (`AiNameGenerator`); the licence texts; developer
  messages (exceptions, `require`, logs, SQL). They are marked for the Step 1 literal guard (see
  there) with a comment saying why.
- **Inline markup stays inside the strings.** `**bold**` and the backtick spans that
  `parseInlineMarkup` understands are part of the translatable text, so a translator can move them.
- **A right-to-left translation is supported, and Arabic is the first.** Its direction, plural forms and numerals follow
  its `common_locale`, and text written the other way is isolated (see above). Before shipping one, render every screen
  in it: there are about 10 absolute left/right usages to check (offsets and `Alignment.*Start/End` are mirrored; absolute
  ones are not), and the canvas art doesn't depend on direction.

## Conventions

- **One file:** `app/shared/src/commonMain/composeResources/values/strings.xml`. Split it by screen
  only if it gets hard to work in, because Compose resources merges every `values/*.xml` file.
  Strings are grouped under an XML comment naming the screen and file, in the Step 4 order.
- **Key names:** `screen_element_purpose`, lower snake case. The screen prefix matches the `ui/`
  package (`game_`, `setup_`, `settings_`, `styles_`, `scores_`, `stats_`, `achievements_`,
  `rules_`, `common_`); `mode_`, `achievement_`, `category_` and `modifier_` for model text.
  Spoken-only strings end in `_spoken` (or `_cd` for a content description) so that a screen's
  visible and spoken strings sit together.
- **Model text keys are derived from the enum entry**, so tests can find them without a lookup
  table: `mode_<id>` for `GameMode` (its stored `id`, e.g. `mode_third_wind`),
  `achievement_<entry name lowercased>_title` / `_description`, `category_<entry name lowercased>`.
- **Arguments are positional** (`%1$s`, `%1$d`) even when there's only one, so a translator can
  reorder them.
- **One sentence per string.** Never join fragments in code; a sentence that varies gets a template
  per variant.
- **Escaping is not Android's.** Checked in Step 0 by rendering probe strings under Robolectric:
  - Apostrophes and double quotes are written plainly: `Don't "quote"`. **Never `\'` or `\"`** -
    Compose resources keeps the backslash, so the player would see `Don\'t`.
  - `\n` (line break) and `\uXXXX` are turned into the character, as on Android.
  - `&` is written `&amp;` (and `<` as `&lt;`), because the file is XML.
  - **A percent sign is a single `%`**, even beside an argument (`%1$d%`). `%%` is *not* collapsed:
    it shows as `%%`. Only `%N$s` and `%N$d` are replaced.
- **Resolve strings in composition, then hand them in.** `stringResource` and
  `pluralStringResource` are composable, so they can't be called inside a `semantics { }` /
  `clearAndSetSemantics { }` block, a `clickable(onClickLabel = ...)` builder's lambda or any other
  non-composable lambda. Resolve them into a `val` just above (see `DiceCup` and `PlayerTab`).
  Outside composition altogether (a ViewModel, a coroutine) use the suspend `getString()` /
  `getPluralString()`.
- **Text helpers that need strings become `@Composable`** (Step 0 did this with `Standing.label()`
  and `spoken()`, which moved from `game/Standings.kt` to `ui/game/PlayerHeaderBar.kt`). The game
  layer keeps the data (`Standing`); the UI turns it into words.
- **A comment over any string whose meaning isn't obvious** from the key (e.g. "spoken by
  TalkBack on the dice cup button"), since translators see only the file.

## Traps already hit

(More, from Steps 1-5 and the first language, are in "Lessons from the first language" below.)

- **`:app:shared`'s host tests are plain JVM, not Robolectric.** Anything that resolves a resource
  (`stringResource`, `getString`) or uses `android.icu` fails there. Options, in order:
  1. Test it through a **public** composable in `:app:android`'s Robolectric tests
     (`app/android/src/test/...`). `internal` isn't visible from that module, so go through the
     screen or component that uses it, as `BoardSemanticsTest` does for the places.
  2. For a guard over the strings themselves, **read `strings.xml` from disk** in an
     `androidHostTest`, the way `StandardPerfectPlayTableTest` reads a bundled file
     (`File("src/commonMain/composeResources/...")` - the working directory is the module).
  3. For the iOS `actual`, an `iosTest` in `app/shared/src/iosTest` (see `OrdinalIosTest`). It
     compiles on Linux (`compileTestKotlinIosSimulatorArm64`) but runs only on a Mac - say so in the
     report.
- **Robolectric needs nothing special.** `Res.string` and `Res.plurals` resolve with the existing
  test setup. `@Config(qualifiers = "fr")` on a test method switches the device language (and
  `Locale.getDefault()`).
- **Cached formatters can hide a bug between tests in one JVM.** `formatOrdinal` keeps its last
  formatter. When checking that a locale test can fail, run that test on its own
  (`--tests '*BoardSemanticsTest.on a phone*'`), or an earlier test's cache can make it pass.
- **`verifyAssetSources` audits `composeResources/`.** It skips `composeResources/values*/`
  (strings). A new non-string file under `composeResources/` still needs an `asset-sources.json`
  entry (`app/licensing/README.md`).
- **The ICU API you expect may not be public.** `RuleBasedNumberFormat` isn't in the Android SDK;
  check a class compiles before designing around it. `MessageFormat`, `ListFormatter` and
  `java.text.NumberFormat` are public.
- **A visible string that's cleared from semantics can't be seen by a semantics test** (the tab's
  "=2nd"). Say so in the report rather than claiming it's covered.

### Step 0 - Spike: one dialog, one plural, one ordinal (done, `d5d29a6`)

### Step 1 - Guards before the bulk work (done)

Add these first, so the extraction can't go backwards and the project rules keep holding. All of them
are `androidHostTest`s in `app/shared/src/androidHostTest/kotlin/net/zodac/dicefive/i18n/` that read
the files from disk (see "Traps already hit"). Put the shared file-reading in one small helper there
(e.g. `StringResourceFiles.kt`: every `src/commonMain/composeResources/values*/strings.xml`, parsed
with `javax.xml.parsers`, giving `locale -> key -> text` for strings and each plural item). Commit
as `[Project]`.

1. **Banned words in the strings.** The existing guards stay where they are (`AchievementEngineTest`
   checks visible achievement text for the trademark; `AchievementTextTest` checks titles). Add one
   that scans **every locale's** strings and plural items for the trademark and for "three of a
   kind", "four of a kind", "five of a kind" (spaced or hyphenated, any case) - the banned words in
   `CLAUDE.md`. Write the trademark into the test the way `AchievementEngineTest` does (lower case,
   in the assertion), since that test is the one permitted exception; don't add another copy
   elsewhere.
2. **Sora subset for the strings that are drawn in Sora.** Today only achievement titles are checked
   (`AchievementTextTest`'s "every title is in the brand font's character set"). Leave that test as
   it is until Step 2 moves the titles; Step 2 then switches it to read the `achievement_*_title`
   keys of every locale. Nothing else to do here in Step 1 - note it in the commit body.
3. **No new literals.** The guard that drives Steps 3-4:
   - Scans `src/commonMain/kotlin/net/zodac/dicefive/ui/**/*.kt` for a string literal containing a
     letter passed as `text =`, `Text("`, `contentDescription =`, `stateDescription =`,
     `onClickLabel =`, `label =`, `title =`, `message =`, `headline =`, `supporting =` or
     `confirmLabel =` / `dismissLabel =` (regexes are fine; it's a guard, not a parser). Include
     `label = "` inside `onClick(label = "...")` too.
   - **Baseline file:** `app/shared/src/androidHostTest/i18n-literal-baseline.txt`, read with
     `File(...)` like the strings (not as a classpath resource), one line per file:
     `<path relative to ui/>\t<count>`, sorted. Generate it once from the current
     code (with a `-PregenerateI18nBaseline` switch, like `-PregeneratePerfectPlayTable` in
     `app/shared/build.gradle.kts`).
   - The test **fails if any file's count is higher than its baseline** (a new literal), and **also if
     it's lower** ("lower the baseline to N" - so the baseline always matches and shrinks with Step
     4). The failure message names the file and the lines.
   - **A literal that must stay** (a mark like "3x", a non-text string) is excluded by putting
     `// i18n: not translated - <why>` at the end of its line. The scan skips those lines.
   - Report the starting total in the commit body.
4. **Missing keys / mismatched arguments.** Every key in any `values-xx/` exists in `values/`, every
   `%N$s`/`%N$d` in a translation appears in the base string, and every base plural has an `other`
   item. Passes trivially today (no `values-xx/`); add a test fixture or a unit test of the
   checking function on hand-made input so it isn't untested.

**What landed:** `app/shared/src/androidHostTest/kotlin/net/zodac/dicefive/i18n/` holds
`StringResourceFiles` (parses every locale's `strings.xml`), `StringChecks` (banned words, translation
vs base, plurals without `other` - pure functions, so they're unit-tested on hand-made input),
`StringResourcesTest` and `NoNewLiteralsTest`. The baseline starts at **175 literals in 34 files** -
the regexes only match the parameters listed above, so it's well under the ~900 estimated for all
text; Step 4 should still grep each screen for literals the guard's patterns don't reach (e.g. list
items, `Text(buildString...)`) and widen the patterns when it finds a family. The Sora subset check
is unchanged until Step 2.

**Done when:** the four tests exist and pass, the baseline is checked in, and `.claude/I18N.md`'s

### Step 2 - The model layer (done)

### Numerals, length limits and the turn timer (added after Step 4)

- **Numerals.** Every whole number that reaches the screen is written in the numerals of the strings' language, which a
  translation sets with the tag in `common_locale` (`ar-u-nu-arab` for Arabic-Indic digits, `fa-u-nu-arabext`, `hi-u-nu-deva`;
  plain `en-GB` is 0-9). Numbers inside a string resource are done by `ui/common/Strings.kt`'s `stringResource` and
  `pluralStringResource`, which every file under `ui/` imports instead of the library's (it fills `%1$d` itself, from the raw
  template); a number drawn or said on its own uses `Int.localised()`; `grouped()` keeps the numerals too. So the cup's
  "x3" becomes "x٣" with no per-string work. `FormattingNumeralsTest` pins the formatter. Code that reads numbers back out
  of text must take any script's digits: the Rules page's spoken scores match `\p{Nd}`, not `\d` (which is 0-9 only), and
  read them with `digitToInt()`. The setup form's number field
  accepts any script's digits. Not covered: digits that are *art* (the pips on a die, the numeral dice styles, which have
  their own systems).
- **Length limits.** The player-name cap (`maxPlayerNameLength`) is in characters' worth of width, not UTF-16 units: full-width
  characters count two and combining marks none (`model/NameWidth.kt`), so a Chinese name gets about half the characters
  and no cut lands inside an emoji or an accent. The achievement-title cap is per language: `achievement_title_max_length`
  in each `strings.xml` (38 for English; a translation lowers or raises it, falls back to English if absent, and
  `AchievementTextTest` holds that language's titles to it) - **a translator must still render the banner in that
  language to check it fits**, since a character count is only a stand-in for width. Other text lives in boxes that
  wrap, scroll or shrink. This loosens CLAUDE.md's flat 38: for English it is unchanged.
- **The turn timer.** The drawn text is a whole string (`game_timer_left`, "Time left: %1$ds" - the unit and its position are
  the translator's, and it may be shortened, as the badge is one centred line), the setup labels are `setup_timer_seconds`
  ("30s" - likewise), the spoken forms are `<plurals>` with the language's own categories, and the digits follow the
  numerals above. Nothing is hard-coded to seconds-as-"s" or to a width.
- **Plurals.** Anything a number changes the grammar of is a `<plurals>` entry, even where English reads the same in both
  forms (so a translator has the hook): "Earned N achievements" (its own plural, joined to the list by a template),
  "N open" / "N more open", "N points, M exact", "N 5x scored", on top of the earlier ones. A string with two numbers
  is split so each noun has its own plural, as Compose resources chooses a form from one number only. No library:
  Compose resources already carries the CLDR plural rules for every language (one, few, many... as that language
  needs), and `StringResourcesTest` checks every English plural spells out `one` and `other`. `PluralFormsTest`
  (Robolectric, for Android's ICU plural rules) checks that every language's plurals have every form its rules give the
  counts 0-100,000, plus `other` - a Russian file needs `few` and `many`, an Arabic one `zero`, `two`, `few` and `many`.
- **Symbols and units a translator owns.** The cup's "x", the timer's "s", the bonus's "+" (`common_bonus_amount`), the
  tie's "=", the "%" and the step's "." are inside whole strings, and the header of `strings.xml` says so:
  the multiplication sign ("×"), its side, the unit and its spacing ("12 s", "12 с", "12秒") are all the translation's
  to write. The Sora face holds Latin-1 (so "×") but not Arabic-Indic digits or non-Latin units, which fall back to the
  system font in those few places.

### Spanish, the first language (Step 5, Android part)

`composeResources/values-es/strings.xml` is a full machine-assisted translation (Spain: tú form, `¿?`/`¡!`, `es-ES`
so numbers group with "." and four-digit numbers stay ungrouped), checked by the same guards as English. The language follows
the **device language** - there is no in-app picker, by decision. What was added for Android: `androidResources {
generateLocaleConfig = true }` in `app/android/build.gradle.kts` (the per-app language setting on Android 13+),
`res/resources.properties` (`unqualifiedResLocale=en-GB`), and `res/values-es/strings.xml` holding only `app_name` -
Android lists a language only if `res/` has a `values-xx` for it, though the app's text is in the shared resources. Every
new language therefore needs **both** `composeResources/values-xx/strings.xml` and `res/values-xx/strings.xml`. The
tests that need a language the app does *not* have use German (`de`) or Persian (`fa`). `SpanishTextTest` shows the formatters in Spanish
(ordinals "1.º puesto", grouping "34.521", `¿`). Still to do for it: a hand check on a device and the Play listing.
`common_timestamp_pattern` is the English one for now; a native speaker may prefer "7 oct 2026, 14:05".

**Fit.** A control sized for the English word can break a longer one ("Usuar / io" on the player-type chip was the first case
found). The rule: a longer language's text fits by its box growing (the chip now measures its two labels) or the text
shrinking, never by splitting a word. `TextFitTest` draws each screen in Spanish at 360dp with real text measurement
(`@GraphicsMode(NATIVE)`; the default mode measures a character as a pixel) and fails if any text breaks inside a word - run it for
a new language by changing its `qualifiers`. It sees only what is on screen (the top of a long list, one Rules page at a time).

**Capitalisation.** English headings are Title Case ("New Game"); Spanish writes headings in sentence case ("Nueva partida",
"Modo de juego"), which is its rule, not an omission, and `values-es` is consistent about it. A translator follows the language's own
convention, not English's.

### Arabic, the first right-to-left language

`composeResources/values-ar/strings.xml` is a full machine-assisted translation in Modern Standard Arabic, with
`res/values-ar/strings.xml` (`app_name` only) beside it for Android's language list. `common_locale` is `ar-u-nu-arab`, so
every number the app formats is in Arabic-Indic digits ("٣٤٬٥٢١"), and the layout is mirrored. How it was done, and what a
right-to-left or many-form language needs that Spanish didn't:

- **All six plural forms** (`zero`, `one`, `two`, `few`, `many`, `other`) for each of the 26 plurals. The base's `%N$d` must stay in
  every form (`StringChecks` requires it), so a dual that would read better with no number ("رميتان") is written "رميتان (٢)".
  `few` is 3-10, `many` 11-99: the noun is plural after 3-10 and singular after 11+.
- **Digits typed into a translation** (in a description, a rules sentence) are written as Western digits in the source and turned into
  Arabic-Indic by script, skipping `%1$d` placeholders and the game's marks (3x, 4x, 5x, 2+2, D20, LCD), which stay Latin and are
  isolated by the sentence's own direction. "," between thousands becomes "٬" and "%" becomes "٪". If a string is edited by hand,
  type Arabic-Indic digits directly.
- **Sora doesn't hold Arabic.** Achievement titles, mode names and the like are drawn in the system font. The Latin-1 guards
  (`AchievementTextTest`, `GameModeTextTest`) skip the folders in `StringChecks.localesOutsideSora`; add a language there only when
  its whole script is outside Sora. The title cap stays 38 characters.
- **Style nouns are indefinite** ("نرد", "كأس نرد", "حصيرة") because they are slotted into "نمط %2$s «%1$s»" and after the prepositions
  ل-: an article would join badly. Quotes are «guillemets».
- **Signs sit first in the string** ("+%1$d", "×%1$d", "=%1$s") and the layout puts them on the right, which is where Arabic reads from.
- **Tests:** `ArabicTextFitTest` re-runs `TextFitTest`'s screens in Arabic (the base class is `open`, with the one language-specific
  string overridable); `ArabicTextTest` covers direction, digits, grouping and plural forms. The tests that need a language the app
  does *not* have now use Persian (`fa`), as Arabic ships.
- **Glossary:** the scorecard categories are *الواحدات, الاثنيات, الثلاثيات, الرباعيات, الخماسيات, السداسيات*, *فول هاوس*,
  *تسلسل صغير / كبير*, *الحظ*; dice cup *كأس النرد*; hold *ثبّت*, release *حرّر*, roll *ارمِ*; scorecard *بطاقة النتائج*; mat *حصيرة*.
  Mode names: *القياسي, ثلاثي الألوان, الإطلاق السريع, ستاد 7 أحجار, النفس الثالث, قائمة الأهداف*. "Alibi" and the marks are not translated.
- **Not verified by a native speaker or on a device.** Still to do: a hand pass for wording and register, a TalkBack pass in Arabic, a look
  at every screen mirrored (the ~10 absolute left/right usages), and the Play listing.

### Adding a language after Step 5

A checklist, from doing it once (Spanish):

1. **Both strings files.** `app/shared/src/commonMain/composeResources/values-xx/strings.xml` (the translation) *and*
   `app/android/src/main/res/values-xx/strings.xml` (just `app_name`, so Android lists the language). Copy the base file;
   every key must be present, with the same `%N$s` / `%N$d` placeholders and the same markup (`` ` ``, `*`, `**`).
2. **`common_locale`** to the language's BCP 47 tag, with any numerals or region it needs: `es-ES` (grouping "34.521"),
   `ar-u-nu-arab` (Arabic-Indic digits). It drives numerals, grouping, ordinals, lists, dates, plural forms and the layout
   direction (right to left for Arabic, Hebrew, Persian...). Reorder `common_timestamp_pattern` for the language's dates.
3. **Every plural category the language has** (CLDR): Russian needs `few` and `many`, Arabic `zero`, `two`, `few` and
   `many`. A missing category falls back to `other` silently at runtime; `PluralFormsTest` catches it.
4. **`achievement_title_max_length`** if 38 characters isn't right for the script; achievement titles and mode names are
   drawn in Sora, which holds Latin-1 only (no `œ`, `’`, `…`; `é ñ ¿ ¡ « » ×` are fine) - anything else falls back to the
   system font.
5. **Run the guards** (`StringResourcesTest`, `AchievementTextTest`, `GameModeTextTest`, `StyleNamesTest`), then
   **`TextFitTest`** with that language in its `qualifiers`, then add a `<Language>TextTest` like `SpanishTextTest` for what
   is specific to it (ordinals, grouping, punctuation).
6. **A device pass in that language**, with TalkBack: the things no test hears (see "Lessons").
7. **The store listing** (`PUBLISHING.md`), under the same banned-words rule.

### Lessons from the first language (Spanish)

**Process that worked**
- **Dump, translate in chunks, assemble by script, validate by script.** Dump the base strings as `key|text` lines, translate
  a couple of hundred at a time into the same format, then build the XML in one step and check it: every base key present,
  same placeholders per key, same markup counts, titles within the cap, no character outside Latin-1 in the Sora-drawn text.
  Doing the glossary decisions *before* the first chunk (below) avoids a normalising pass afterwards.
- **Transform mechanically, then read the diff.** Moving ~1,000 strings out of Kotlin was a Python pass per screen (regexes
  over `text(...)`, `title = ...` and so on, generating keys, the XML and the imports) plus a compile; the compiler found
  every non-composable call site. A small helper that adds `Res.string.*` imports and appends XML sections (it lived in the
  session's scratch directory, not the repo) saved most of the effort.
- **Chain build commands with `&&`.** A `;` after a failing `gradlew` let a commit go in with a failing test once; it had to be
  amended.
- **A guard that can't fail isn't a guard.** `TextFitTest` passed first time in Robolectric's default mode because that mode
  measures every character as one pixel; it only found the broken "Usuario" after `@GraphicsMode(NATIVE)`. Check a new guard
  fails when the thing it guards is broken (it was: the fix was removed and the test failed).

**Technical traps**
- **Anything left to "the device's language" leaks it into an untranslated app.** Found in the RTL review: Compose's layout
  direction (from the configuration), Compose resources' plural rules (from `LocaleList.getDefault()`), `DateTimeFormatter`
  without a locale, and Android's own resources (Material labels, the system copy menu). Each now follows `common_locale`
  (`StringsLanguage`, `stringsLanguageConfiguration`, `formatTimestamp`). A new formatter or platform API must too; check it
  on a phone in a language the app doesn't have (`@Config(qualifiers = "ar")` / `"ru"`).
- **Compose resources' environment is internal API** (`LocalComposeEnvironment`, `ResourceEnvironment`'s constructor,
  `PluralRuleList`): you can't set the plural language for one composition. Hence aligning the process's `LocaleList`.
- **Text with no `textDirection` is laid out in the layout direction, not by its content.** English in an RTL layout became
  RTL paragraphs (".dice", "of 11 1"). Use `TextDirection.Content` for text whose language isn't the UI's (player names,
  the licences).
- **`\d` is 0-9 only** (JVM and Native regex). Parse numbers the app formatted with `\p{Nd}` and `digitToInt()`.
- **Lowercasing or capitalising translated text in code** is wrong for some languages (German nouns); give the variant its
  own string instead (the stepper buttons, the Rules' coloured dice).
- **Russian's plural `other` is for fractions only**, so integers never reach it; `PluralFormsTest` adds `other` itself.
  ICU's rules are only on Android, which is why that guard is a Robolectric test.
- **Lint's `AppBundleLocaleChanges`** fires on `Configuration.setLocales`; suppressed on `stringsLanguageConfiguration` because
  it only ever switches to the base language, which every split has. If it ever switches to a translation, disable Play's
  language splits instead (`bundle { language { enableSplit = false } }`).
- **`Res` is internal to `:app:shared`**, so `:app:android` tests can't resolve a string. They read English from
  `strings.xml` on disk (`englishText()` in `StyleTestSupport.kt`) or go through a public composable. `shared` exposes the
  resources library as `api` because `StyleFamily`, `UnlockedStyle`, `LicenceLabels` and others carry `StringResource`s.
- **Compose resources' own `stringResource` can't be trusted with numerals**, so every UI file imports
  `net.zodac.dicefive.ui.common.stringResource` / `pluralStringResource` (`Strings.kt`), which fill the placeholders
  themselves. Importing the library's by mistake compiles and silently skips the numerals.
- **A string drawn by Android views** (the Licences list) gets its words through a public composable that hands plain strings
  over (`licenceLabels`), not a second set of Android resources.
- **`generateLocaleConfig` only sees `res/values-xx`**, not Compose resources - hence the `app_name`-only file per language.
- **A language the app doesn't have**, for tests that check "stays English": use German (`de`), not one that ships.
- **Plural categories come from one number only.** A sentence with two counts is split so each noun has its own plural.
- **Text in a box sized for English** is the commonest defect (the player-type chip, first). Prefer a box that measures its
  longest label; shrink text only if it stays at or above the 12sp floor.
- **Semantics-cleared text can't be tested** (a node that sets its own `contentDescription` hides its text from the finder);
  use `useUnmergedTree = true`, or say it's untested.

**Translation decisions** (Spanish; a glossary a future translator should match, and one a new language should make for itself)
- Register: informal "tú". Headings and buttons in **sentence case** ("Nueva partida"), as Spanish writes them - English's
  Title Case is not carried over. Punctuation: `¿ ?`, `¡ !`; `×` for the cup's multiplication sign; no-break space before
  `pts` and the timer's `s` so a number never parts from its unit.
- Game terms: Standard *Estándar*, Tricolour *Tricolor*, Quickfire *Ráfaga*, 7 Dice Stud *Stud de 7 dados*, Third Wind *Tercer
  aliento*, Hit List *Lista de objetivos*; hold *conservar*, release *soltar*, roll *tirar*, dice cup *cubilete*, mat *tapete*,
  scorecard *tarjeta*, slot *ranura*; boxes *Unos, Doses, Treses, Cuatros, Cincos, Seises*, *Full*, *Escalera pequeña / grande*,
  *Azar*, *Doble pareja*, *Pares / Impares*, *Full de colores*. The game's marks (3x, 4x, 5x, Alibi, 2+2) are never translated.
- Where English reuses a word for two things (Rose / Pink, Opening), pick distinct translations (*Rosa antiguo* / *Rosa*).
- **Not verified by a native speaker or on a device.** The first pass is machine-assisted; the device pass (item 6) is where
  awkward wording and truncation get caught.

## Effort

Steps 1-3: about two sessions. Step 4: two or three sessions of repetitive work. The APK size
change is negligible (one resource table; no new library).
