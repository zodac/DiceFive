# DiceFive: internationalisation (i18n)

Every player-visible and spoken string lives in Compose resources, so a language is added by adding files. The app
ships **English** (`en-GB`, the base, British spelling), **Spanish** (`es`) and **Arabic** (`ar`, right to left). The
translations, glossaries and adding a language are in `I18N_LANGUAGES.md`. The banned words apply to every language
and to the store listing.

**The rule: no partial translations.**
- The app is either wholly in a language it has a `values-xx` for (text, plurals, numerals, dates, layout direction,
  and Android's own text), or wholly in English, left to right.
- The licences stay English and left to right in every language.
- Only the device's first language counts. An Arabic phone whose second language is Spanish gets English.

## Working with strings

All strings go in one file, `app/shared/src/commonMain/composeResources/values/strings.xml`, plus every
`values-xx/strings.xml`. They're grouped under an XML comment naming the screen and file:

```xml
<!-- Leave game confirmation (ui/game/LeaveGameConfirmation.kt) -->
<string name="game_leave_title">Leave game?</string>
```

```kotlin
import net.zodac.dicefive.resources.Res
import net.zodac.dicefive.resources.game_leave_title           // one import per key; unresolved until Gradle compiles once
import net.zodac.dicefive.ui.common.stringResource             // OURS, not org.jetbrains.compose.resources - see numerals

title = stringResource(Res.string.game_leave_title)
stringResource(Res.string.game_standing_spoken, ordinal(place))          // "%1$s place"
pluralStringResource(Res.plurals.game_cup_cd, rolls, rolls)              // the count twice: form, then argument
```

- **Import `net.zodac.dicefive.ui.common.stringResource`/`pluralStringResource`** (`Strings.kt`) in every UI file. The
  library's own version compiles fine and silently skips localising the numerals.
- **Resolve in composition, then hand the result in.** These functions are composable, so they can't be called inside
  `semantics { }`, `clearAndSetSemantics { }`, an `onClick` or any other non-composable lambda. Resolve into a `val`
  just above (see `DiceCup`, `PlayerTab`). Outside composition (view models, coroutines), use the suspend
  `getString()`/`getPluralString()`.
- **Text helpers that need strings are `@Composable`** (`Standing.label()`). The game layer keeps the data; the UI
  turns it into words.

### Conventions

- **Key names**: `screen_element_purpose`, in lower snake case.
  - The screen prefix matches the `ui/` package: `game_`, `setup_`, `settings_`, `styles_`, `scores_`, `stats_`,
    `achievements_`, `rules_`, `common_`.
  - Model text uses `mode_`, `achievement_`, `category_` and `modifier_`.
  - Spoken-only strings end in `_spoken`, or `_cd` for a content description.
- **Model keys are derived from the enum**, so tests find them without a lookup table: `mode_<id>`,
  `achievement_<entry lowercased>_title`/`_description`, `category_<entry lowercased>`.
- **Arguments are positional** (`%1$s`, `%1$d`), even when there's only one.
- **One sentence per string.** Never join fragments in code; give each variant its own template.
  - The exception is sentences whose pieces come and go (a box's spoken state, a Rules example, a Statistics card).
    These join clause strings with `common_clauses_join`/`common_sentences_join`, folded pair by pair, so a language
    can change the separator.
  - Avoid whitespace-only strings, which get trimmed.
- **Escaping is not Android's** (checked by rendering):
  - Write `'` and `"` plainly. **Never `\'` or `\"`**: the backslash shows on screen.
  - `\n` and `\uXXXX` work.
  - Write `&amp;` and `&lt;` (it's XML).
  - **A percent sign is a single `%`**, even next to an argument (`%1$d%`). `%%` shows as `%%`.
- **Comment any string whose meaning isn't obvious** from its key, because translators see only the file.
- **Inline markup** (`**bold**`, backtick spans for `parseInlineMarkup`) stays inside the string, so a translator can
  move it.
- **Never upper- or lower-case translated text in code** (German capitalises nouns, for one). Give each variant its own
  string.

### Plurals

Plurals use `<plurals>` with `pluralStringResource`/`getPluralString`. `components-resources` ships the CLDR rule tables
in common code, so plural choice needs no library. A hand-rolled `plural()` or an
ICU/moko/Lyricist library were rejected: they duplicate what's bundled and add to the APK.

```xml
<plurals name="game_cup_cd">
    <item quantity="one">Dice cup, %1$d roll left</item>
    <item quantity="other">Dice cup, %1$d rolls left</item>
</plurals>
```

- **Pluralise the whole phrase**, never `"$n " + noun`.
- **Every form includes `%1$d`**, `one` too. In some languages `one` covers 21, 31 and so on.
- **Zero is not a form.** English has no `zero` category, so "None" is a separate string chosen with `if (n == 0)`.
- **Any number that changes the grammar gets a plural**, even when English reads the same either way, and even when it
  only changes a verb.
- **A string with two counts is split**, because the form is chosen from one number only.
- `StringResourcesTest` checks English has `one` and `other`. `PluralFormsTest` (Robolectric, ICU) checks every
  language has every form its rules need for 0-100,000.

### Numbers, ordinals, lists and dates

CLDR plurals are cardinal only. Ordinals, grouping, lists and dates go through each platform's formatter, behind
`expect`/`actual` (`ui/common/Formatting.kt`):

| Helper                          | Android                                                                                |
|---------------------------------|----------------------------------------------------------------------------------------|
| `ordinal(n)`/`formatOrdinal`    | `android.icu.text.MessageFormat("{0,ordinal}")` (`RuleBasedNumberFormat` isn't public) |
| `Int.grouped()`                 | `java.text.NumberFormat.getIntegerInstance(locale)`                                    |
| `spokenList(items)`             | `android.icu.text.ListFormatter`                                                       |
| `timestamp()`/`formatTimestamp` | `java.time`                                                                            |

- **Formatters use the strings' language, never the device's.** Each strings file sets `common_locale`, which the
  composable helpers pass to the `expect fun formatX(..., languageTag)`. Without it, a French phone would get English
  text with "1er" in among it (`BoardSemanticsTest` runs under `fr`).
- **Lists** follow `common_list_locale` instead, usually the same tag. English sets en-US, whose lists have the Oxford
  comma ("6, 6, and 6") that en-GB's leave out. Write any list in an English string with one too.
- **The words around a formatted value** ("tied", "place") go in string templates, not in the helper.
- **Dates.** The pattern is a string (`common_timestamp_pattern`), so translators can reorder it. A device already in
  the strings' language keeps its regional form ("Sep" on en-US).
- **Numerals.** Every whole number shown is in the numerals of the strings' language (`common_locale`, e.g.
  `ar-u-nu-arab`).
  - Our `stringResource` fills `%1$d` itself.
  - A lone number uses `Int.localised()`, and `grouped()` keeps the numerals.
  - Code that reads numbers back from text must match `\p{Nd}` and use `digitToInt()`; `\d` is 0-9 only.
  - Digits that are *art* (pips, numeral dice) are their own system.
  - Tests: `FormattingNumeralsTest`.
- **Symbols and units belong to the translator**: the cup's "x", the timer's "s", "+" (`common_bonus_amount`), "=",
  "%" and the step's ".". They're inside whole strings (`game_timer_left` "Time left: %1$ds",
  `setup_timer_seconds`), and the header of `strings.xml` says so.

### Layout direction and Android's own text

`StringsLanguage` (`ui/common/StringsLanguage.kt`), applied by `DiceFiveTheme`, makes three things follow the
strings' language instead of the device's:

- **Layout direction.** `android:supportsRtl` is on. `LocalLayoutDirection` comes from `common_locale`
  (`isRightToLeft`), so an Arabic phone getting English isn't mirrored.
  - The Licences list is always left to right, each paragraph reading by its first letter (`LicensesDialogTest`).
- **Plural forms.** Compose resources picks a form by `LocaleList.getDefault()`, and its environment is internal API.
  So `alignPlatformLanguage` puts the strings' language first in the process's `LocaleList` on each composition
  (Android resets it when the device language changes).
  - Without this, a Russian phone would read "21 solo game".
- **Android's own text** (Material's built-in labels, the copy-and-paste menu).
  `MainActivity.attachBaseContext` applies `stringsLanguageConfiguration()` when the device's first language isn't one
  the app has (`MainActivityLanguageTest`).
  - Lint's `AppBundleLocaleChanges` is suppressed there, because it only ever switches to the base language. If that
    changes, disable Play's language splits instead.
- **Text in the other direction** (an Arabic name in English text, "5x" in Arabic) is wrapped in U+2068/U+2069 by
  `fill()` in `ui/common/Strings.kt`.
  - Same-direction text is untouched. A mark typed inside a translation is the translator's to isolate.
  - Tests: `BidiIsolationTest`.
- **Name fields** use `TextDirection.Content`, and so does any text not in the UI's language.
- Tests: `StringsLanguageTest` (under `ar`, `fa`, `iw`, `ru`).

**A new formatter or platform text API must follow `common_locale` too.** Test it under
`@Config(qualifiers = "ar")`/`"ru"`, and use German (`de`) as "a language we don't ship".

### Never translated

These stay in code:
- the game's marks ("3x", "4x", "5x", "2+2", "Alibi");
- the English-name easter eggs (`IrishEasterEgg`, `SolutionEasterEgg`);
- `AiNameGenerator`, and the logo's "DiceFive";
- animation labels, and the debug "Superuser mode activated!" toast;
- the licence texts, and developer messages (exceptions, `require`, logs, SQL).

Each such literal under `ui/` ends its line with `// i18n: not translated - <why>`; `NoNewLiteralsTest` fails on any
other.

**What a player types is never translated; defaults are.** An empty name uses `common_default_player_name`. Names are
fixed once a game starts, so switching language starts a new "Joueur 1" beside an old "Player 1".

The app follows the device's language. There is no in-app picker.

## Where the text lives

- **Model text** is a `StringResource` on the model: `Achievement.title`/`description`, `AchievementCategory.label`,
  `GameMode.displayName`/`description`, `PlayerColour.label`, `StyleGroup.name`/`StyleVariant.name`
  (`style_colour_<word>`, shared), and `StyleRegistry.noun`/`variantNoun` (all in `game/style/StyleRegistries.kt`).
- **Box and die-colour names** are spoken only (`score_<name>`, `die_colour_<name>`, via `spokenName()` in
  `BoardSemantics.kt`).
- **Rules page**: `rules_<page>_title`, `_tab`, `_<n>`. Headings are `RulesName`; scores are `RulesScore`, drawn
  through `rules_points_short` ("%1$dpts") and spoken through the `rules_points_spoken` plural.
- **Text for a platform view** (Android's licence list) comes from a public composable that hands over plain strings
  (`licenceLabels`), never a second set of Android resources.
- **The guards**:
  - `NoNewLiteralsTest`. Widen its patterns if a new text-taking call appears.
  - `StringResourcesTest`: banned words in every locale, keys and arguments, plurals.
  - `AchievementTextTest`, `GameModeTextTest`, `StyleNamesTest`.
  - `PluralFormsTest`.
  - `TextFitTest`: no word broken across lines.
  - Most are `androidHostTest`s reading every language's file from disk (`StringResourceFiles`).
- **Not covered by a test** (cleared from semantics or internal): the cup's visible "x3", the timer badge's text, and
  the drawn "=2nd". Say so.

## Verify

The `test` skill's full gate, plus:

- **Moving text is word for word.** A test asserting the English still passes unchanged. **Never edit a test's
  expected English to make it pass.**
- **Spoken text has a test** asserting it word for word.
- **Every language has the key**, translated, with the same placeholders and markup (`StringResourcesTest`).
- **The report says what TalkBack should say.**

## Traps already hit

- **A UI test resolves `Res` with nothing special**, on both targets (`UiTest`, `.claude/skills/test`). A check of every
  language's file reads `strings.xml` from disk in an `androidHostTest` instead (`StringResourceFiles`; the working directory is
  the module).
- **Another language is Robolectric's**: `@Config(qualifiers = "fr")` switches the device language, so a test in one
  lives in `:app:shared`'s `androidHostTest`. `android.icu` is there too; the JVM target has ICU4J.
- **`Res` is internal to `:app:shared`.** `shared` exposes the resources library as `api`, because models carry
  `StringResource`s.
- **`verifyAssetSources` audits `composeResources/`** except `values*/`. A new non-string file there needs an
  `asset-sources.json` entry.
- **Check an ICU class is public before designing around it.**
- **`generateLocaleConfig` sees only `res/values-xx`**, hence the `app_name`-only file per language.
- **A box sized for English** is the commonest defect. Prefer a box that measures its longest label; shrink text only
  down to 12sp.
