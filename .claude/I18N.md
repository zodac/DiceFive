# DiceFive: internationalisation (i18n) and localisation (l10n)

The plan for moving every player-visible and spoken string out of Kotlin and into string
resources (i18n), so that adding a language later (l10n) is a matter of adding one file per
language. **No other language is planned yet.** Every step up to and including Step 4 is
mechanical, ships English only, and **must change nothing a player sees or hears.**

This file is written so that an agent new to the project can pick up the next step on its own.
Read "Picking up a step" first, then the step itself.

### How to move a string (the worked example)

Before (`LeaveGameConfirmation.kt`):

```kotlin
DiceFiveDialog(
    title = "Leave game?",
    ...
)
```

After - the string in `strings.xml`, under a comment naming the screen:

```xml
<!-- Leave game confirmation (ui/game/LeaveGameConfirmation.kt) -->
<string name="game_leave_title">Leave game?</string>
```

and in Kotlin:

```kotlin
import net.zodac.dicefive.resources.Res
import net.zodac.dicefive.resources.game_leave_title
import org.jetbrains.compose.resources.stringResource

DiceFiveDialog(
    title = stringResource(Res.string.game_leave_title),
    ...
)
```

Each key needs its own import (`net.zodac.dicefive.resources.<key>`). The `Res` accessors are
generated by the build, so a new key shows up as unresolved until Gradle compiles once.

With an argument: `<string name="game_standing_spoken">%1$s place</string>` and
`stringResource(Res.string.game_standing_spoken, ordinal(place))`.

A plural (see "Plurals" below): `pluralStringResource(Res.plurals.game_cup_cd, rolls, rolls)`.

Inside a non-composable lambda (`semantics { }`, `clearAndSetSemantics { }`, an `onClick`),
resolve first and use the `val`:

```kotlin
val rollLabel = stringResource(Res.string.game_cup_roll_action)
val cupDescription = cup?.let { pluralStringResource(Res.plurals.game_cup_cd, it.rollsRemaining, it.rollsRemaining) }
Box(
    modifier = Modifier.clearAndSetSemantics {
        contentDescription = cupDescription.orEmpty()
        onClick(label = rollLabel) { ... }
    },
)
```

### Verify (all of it, every time)

From `/work`:

```sh
# Everything that has to pass before a commit. -q hides warnings, but warnings fail the build
# here anyway (allWarningsAsErrors, lint warningsAsErrors).
./gradlew -q :app:shared:testAndroidHostTest :app:android:testDebugUnitTest \
  :app:shared:lint :app:android:lintDebug \
  :app:shared:compileKotlinIosSimulatorArm64 :app:shared:compileTestKotlinIosSimulatorArm64 \
  assembleDebug
```

While iterating, a single Robolectric class: `./gradlew -q :app:android:testDebugUnitTest --tests '*BoardSemanticsTest'`.
Failures are in `app/android/build/test-results/testDebugUnitTest/TEST-*.xml` (grep for `<failure`).

Then:

- **Word for word.** For every string moved, the old literal and the new resource text are
  identical, including punctuation and spacing (`git diff` - the removed Kotlin literal and the added
  XML line should read the same).
- **Tests that assert on the text still pass unchanged.** If a test asserted on English text and
  still passes, the move was right. Never edit a test's expected English to make it pass - that
  means the text changed.
- **Spoken text has a test.** If a moved spoken string (a `contentDescription`, `stateDescription`,
  action label, announcement) isn't asserted word for word anywhere, add a Robolectric assertion
  for it (Step 0 did this for the cup in `GameScreenCupGateTest`).
- **Build the APK and send it** (`app/android/build/outputs/apk/debug/`), per `CLAUDE.md`, saying
  what to check by hand - including what TalkBack should say, since it hasn't been heard on a device.

## Where things stood before Step 0

- **No string resources existed.** The only one was `app_name` in
  `app/android/src/main/res/values/strings.xml` (the launcher label, which stays there). Every other
  string was a Kotlin literal: roughly 900-1,100 of them across the 183 files in `app/shared`.
  - About 85% were in `ui/`. `RulesScreen.kt` alone had about 120 prose lines; Setup, Settings,
    Styles and Statistics had 20-40 each.
  - The rest was display text held by the model, game and data layers: `GameMode.displayName`,
    `AchievementCategory.label`, the titles and descriptions of the ~87 achievements, the score
    category names, the modifier and difficulty names, `Standing.label()` / `spoken()`
    (`game/Standings.kt`, moved in Step 0), and the banner text in `data/achievements` ("New
    Personal Best").
- **The resource system was already in place.** Compose Multiplatform resources were already used
  for drawables and fonts (`composeResources/`, with `Res` in `net.zodac.dicefive.resources`). The
  same system handles `<string>`, `<plurals>` and `<string-array>`, with `values-xx/` locale folders,
  from one set of files, on both Android and iOS. No new library is needed.
- **Nothing saved holds display text.** The Leaderboard stores `gameModeId`; achievements are
  stored by id. Moving text into resources needs no Room or JSON migration.
- **English grammar was built into the code in about 15 places:**
  - About 10 hand-rolled plurals (`if (n == 1) "roll" else "rolls"`): `DiceCupPanel` (done in Step
    0), `GameScreen`'s timer, `StylesScreen`'s unlock counts, `LicensesDialog`'s `ComponentKind`,
    `AchievementAnnouncements`, `RulesScreen`'s "is/are locked".
  - English ordinals in `Standings.ordinal` (done in Step 0).
  - `grouped()` (`ui/common/Formatting.kt`) hard-codes `,` as the thousands separator.
  - `spokenList()` (`RulesScreen.kt`) joins with ", " and " and ".
  - Sentences assembled from pieces, e.g. `targetProgress` and `stackedSpokenState` in
    `ScoreGrid.kt` (`"$rolled of $n rolled, $inPlace in place"`, a `listOfNotNull(...)` joined with
    ", " and then capitalised). Word order can't be translated when a sentence is built like that.
- **Dates were already localised:** `formatTimestamp` uses each platform's own date APIs.

## Decisions

### Plurals: externalised in `<plurals>`, using Compose resources' own CLDR rules

Three options were weighed:

| Option | Verdict |
|---|---|
| Roll our own `plural(locale, n)` function | **No.** Plural rules are CLDR data, not logic worth owning: Russian, Polish and Arabic have 3-6 categories, and "one" in Russian also covers 21, 31, 101... Every new language would mean new hand-written rules and tests. |
| A library (e.g. an ICU port, or a KMP i18n library such as moko-resources or Lyricist) | **No.** It would duplicate what's already bundled, add classes to the APK (the project already turned down kotlinx-datetime for ~180 classes - see `formatTimestamp`), and moko/Lyricist would replace the resource system rather than extend it. |
| **`<plurals>` in `strings.xml`, read with `pluralStringResource` / `getPluralString`** | **Yes.** `components-resources` 1.12 ships the CLDR plural rule tables in its own `commonMain` (`org.jetbrains.compose.resources.plural.PluralRuleLists`, indexed by locale), so plural selection is the same on Android and iOS, and needs no platform code. A translator supplies the forms their language needs, in the same file as every other string. |

How plurals are written (the real one, from Step 0):

```xml
<plurals name="game_cup_cd">
    <item quantity="one">Dice cup, %1$d roll left</item>
    <item quantity="other">Dice cup, %1$d rolls left</item>
</plurals>
```

```kotlin
pluralStringResource(Res.plurals.game_cup_cd, rolls, rolls)
```

Rules for plurals:

- **The whole phrase goes in the plural, not just the noun.** "%1$d rolls left" is one plural;
  never `"$n " + plural(noun)`. Other languages inflect the verb and adjectives too.
- **Always include the number (`%1$d`) in every form, including `one`.** In some languages `one`
  covers 21, 31 and so on, so "a roll" or a hard-coded "1" would be wrong there.
- **The count is passed twice:** once to choose the form, once as the format argument.
- **Zero is not a plural form.** English has no `zero` category in CLDR, so "None" or "No
  achievements" is a separate `<string>`, chosen in code with an explicit `if (n == 0)`.
- **A plural that only changes a verb is still a plural**, e.g. "The %1$s is locked in chains" /
  "The %1$s are locked in chains".

### Ordinals and number formatting: each platform's formatter, behind `expect`/`actual`

CLDR plural tables in Compose resources are **cardinal only** - they can't produce "1st / 2nd /
3rd". Ordinals, thousands separators and spoken lists go through each platform's formatter, the way
`formatTimestamp` already does:

| Helper | Android (minSdk 26) | iOS |
|---|---|---|
| `ordinal(n)` / `formatOrdinal` (done, `ui/common/Formatting.kt`) | `android.icu.text.MessageFormat("{0,ordinal}")` - ICU's `RuleBasedNumberFormat` would be the direct route but isn't in the public SDK | `NSNumberFormatter` with `NSNumberFormatterOrdinalStyle` |
| `Int.grouped()` (Step 3) | `java.text.NumberFormat.getIntegerInstance(locale)` | `NSNumberFormatter` with `NSNumberFormatterDecimalStyle` |
| `spokenList(items)` (Step 3) | `android.icu.text.ListFormatter.getInstance(locale)` | `NSListFormatter` |

The surrounding words ("tied", "place") go into string templates (`"tied %1$s place"`), not
into the helper.

**These formatters use the strings' language, not the device's.** `values/strings.xml` holds
`common_locale` (`en-GB`), and each translation sets its own. The composable `ordinal()` reads it and
passes it to `formatOrdinal(number, languageTag)`, the `expect`/`actual` function. Without this, a
French phone would get English text (no French file to resolve to) with "1er" in among it.
`BoardSemanticsTest` runs the player tabs under `@Config(qualifiers = "fr")` to check this. Step 3
gives `grouped()` and `spokenList` the same shape: a composable that reads `common_locale`, over an
`expect fun formatX(..., languageTag: String)`.

**Dates are the exception for now:** `formatTimestamp` has used the device's month names since
before this work, and is left as it was until a language is added. Then it should take
`common_locale` too.

### Other decisions

- **Base locale is British English.** The copy uses British spelling ("colour", "licence"), so
  the default `values/` should be declared as `en-GB` when the platform plumbing lands in Step 5.
- **These stay in code and are never translated:** the game's marks ("3x", "4x", "5x", "2+2",
  "Alibi"); the easter eggs that are triggered by English names (`IrishEasterEgg`,
  `SolutionEasterEgg`); the CPU name generator (`AiNameGenerator`); the licence texts; developer
  messages (exceptions, `require`, logs, SQL). They are marked for the Step 1 literal guard (see
  there) with a comment saying why.
- **Inline markup stays inside the strings.** `**bold**` and the backtick spans that
  `parseInlineMarkup` understands are part of the translatable text, so a translator can move them.
- **Right-to-left layout is out of scope** until Arabic or Hebrew is wanted. There are about 10
  absolute left/right usages to fix then; the canvas art doesn't depend on direction.

## Conventions

- **One file:** `app/shared/src/commonMain/composeResources/values/strings.xml`. Split it by screen
  only if it gets hard to work in, because Compose resources merges every `values/*.xml` file.
  Strings are grouped under an XML comment naming the screen and file, in the Step 4 order.
- **Key names:** `screen_element_purpose`, lower snake case. The screen prefix matches the `ui/`
  package (`game_`, `setup_`, `settings_`, `styles_`, `scores_`, `stats_`, `achievements_`,
  `rules_`, `common_`); `mode_`, `achievement_`, `category_` and `modifier_` for model text.
  Spoken-only strings end in `_spoken` (or `_cd` for a content description) so that a screen's
  visible and spoken strings sit together.
- **Model text keys are derived from the enum entry**, so tests can find them without a lookup
  table: `mode_<id>` for `GameMode` (its stored `id`, e.g. `mode_third_wind`),
  `achievement_<entry name lowercased>_title` / `_description`, `category_<entry name lowercased>`.
- **Arguments are positional** (`%1$s`, `%1$d`) even when there's only one, so a translator can
  reorder them.
- **One sentence per string.** Never join fragments in code; a sentence that varies gets a template
  per variant.
- **Escaping is not Android's.** Checked in Step 0 by rendering probe strings under Robolectric:
  - Apostrophes and double quotes are written plainly: `Don't "quote"`. **Never `\'` or `\"`** -
    Compose resources keeps the backslash, so the player would see `Don\'t`.
  - `\n` (line break) and `\uXXXX` are turned into the character, as on Android.
  - `&` is written `&amp;` (and `<` as `&lt;`), because the file is XML.
  - **A percent sign is a single `%`**, even beside an argument (`%1$d%`). `%%` is *not* collapsed:
    it shows as `%%`. Only `%N$s` and `%N$d` are replaced.
- **Resolve strings in composition, then hand them in.** `stringResource` and
  `pluralStringResource` are composable, so they can't be called inside a `semantics { }` /
  `clearAndSetSemantics { }` block, a `clickable(onClickLabel = ...)` builder's lambda or any other
  non-composable lambda. Resolve them into a `val` just above (see `DiceCup` and `PlayerTab`).
  Outside composition altogether (a ViewModel, a coroutine) use the suspend `getString()` /
  `getPluralString()`.
- **Text helpers that need strings become `@Composable`** (Step 0 did this with `Standing.label()`
  and `spoken()`, which moved from `game/Standings.kt` to `ui/game/PlayerHeaderBar.kt`). The game
  layer keeps the data (`Standing`); the UI turns it into words.
- **A comment over any string whose meaning isn't obvious** from the key (e.g. "spoken by
  TalkBack on the dice cup button"), since translators see only the file.

## Traps already hit

- **`:app:shared`'s host tests are plain JVM, not Robolectric.** Anything that resolves a resource
  (`stringResource`, `getString`) or uses `android.icu` fails there. Options, in order:
  1. Test it through a **public** composable in `:app:android`'s Robolectric tests
     (`app/android/src/test/...`). `internal` isn't visible from that module, so go through the
     screen or component that uses it, as `BoardSemanticsTest` does for the places.
  2. For a guard over the strings themselves, **read `strings.xml` from disk** in an
     `androidHostTest`, the way `StandardPerfectPlayTableTest` reads a bundled file
     (`File("src/commonMain/composeResources/...")` - the working directory is the module).
  3. For the iOS `actual`, an `iosTest` in `app/shared/src/iosTest` (see `OrdinalIosTest`). It
     compiles on Linux (`compileTestKotlinIosSimulatorArm64`) but runs only on a Mac - say so in the
     report.
- **Robolectric needs nothing special.** `Res.string` and `Res.plurals` resolve with the existing
  test setup. `@Config(qualifiers = "fr")` on a test method switches the device language (and
  `Locale.getDefault()`).
- **Cached formatters can hide a bug between tests in one JVM.** `formatOrdinal` keeps its last
  formatter. When checking that a locale test can fail, run that test on its own
  (`--tests '*BoardSemanticsTest.on a phone*'`), or an earlier test's cache can make it pass.
- **`verifyAssetSources` audits `composeResources/`.** It skips `composeResources/values*/`
  (strings). A new non-string file under `composeResources/` still needs an `asset-sources.json`
  entry (`app/licensing/README.md`).
- **The ICU API you expect may not be public.** `RuleBasedNumberFormat` isn't in the Android SDK;
  check a class compiles before designing around it. `MessageFormat`, `ListFormatter` and
  `java.text.NumberFormat` are public.
- **A visible string that's cleared from semantics can't be seen by a semantics test** (the tab's
  "=2nd"). Say so in the report rather than claiming it's covered.

### Step 1 - Guards before the bulk work (done)

Add these first, so the extraction can't go backwards and the project rules keep holding. All of them
are `androidHostTest`s in `app/shared/src/androidHostTest/kotlin/net/zodac/dicefive/i18n/` that read
the files from disk (see "Traps already hit"). Put the shared file-reading in one small helper there
(e.g. `StringResourceFiles.kt`: every `src/commonMain/composeResources/values*/strings.xml`, parsed
with `javax.xml.parsers`, giving `locale -> key -> text` for strings and each plural item). Commit
as `[Project]`.

1. **Banned words in the strings.** The existing guards stay where they are (`AchievementEngineTest`
   checks visible achievement text for the trademark; `AchievementTextTest` checks titles). Add one
   that scans **every locale's** strings and plural items for the trademark and for "three of a
   kind", "four of a kind", "five of a kind" (spaced or hyphenated, any case) - the banned words in
   `CLAUDE.md`. Write the trademark into the test the way `AchievementEngineTest` does (lower case,
   in the assertion), since that test is the one permitted exception; don't add another copy
   elsewhere.
2. **Sora subset for the strings that are drawn in Sora.** Today only achievement titles are checked
   (`AchievementTextTest`'s "every title is in the brand font's character set"). Leave that test as
   it is until Step 2 moves the titles; Step 2 then switches it to read the `achievement_*_title`
   keys of every locale. Nothing else to do here in Step 1 - note it in the commit body.
3. **No new literals.** The guard that drives Steps 3-4:
   - Scans `src/commonMain/kotlin/net/zodac/dicefive/ui/**/*.kt` for a string literal containing a
     letter passed as `text =`, `Text("`, `contentDescription =`, `stateDescription =`,
     `onClickLabel =`, `label =`, `title =`, `message =`, `headline =`, `supporting =` or
     `confirmLabel =` / `dismissLabel =` (regexes are fine; it's a guard, not a parser). Include
     `label = "` inside `onClick(label = "...")` too.
   - **Baseline file:** `app/shared/src/androidHostTest/i18n-literal-baseline.txt`, read with
     `File(...)` like the strings (not as a classpath resource), one line per file:
     `<path relative to ui/>\t<count>`, sorted. Generate it once from the current
     code (with a `-PregenerateI18nBaseline` switch, like `-PregeneratePerfectPlayTable` in
     `app/shared/build.gradle.kts`).
   - The test **fails if any file's count is higher than its baseline** (a new literal), and **also if
     it's lower** ("lower the baseline to N" - so the baseline always matches and shrinks with Step
     4). The failure message names the file and the lines.
   - **A literal that must stay** (a mark like "3x", a non-text string) is excluded by putting
     `// i18n: not translated - <why>` at the end of its line. The scan skips those lines.
   - Report the starting total in the commit body.
4. **Missing keys / mismatched arguments.** Every key in any `values-xx/` exists in `values/`, every
   `%N$s`/`%N$d` in a translation appears in the base string, and every base plural has an `other`
   item. Passes trivially today (no `values-xx/`); add a test fixture or a unit test of the
   checking function on hand-made input so it isn't untested.

**What landed:** `app/shared/src/androidHostTest/kotlin/net/zodac/dicefive/i18n/` holds
`StringResourceFiles` (parses every locale's `strings.xml`), `StringChecks` (banned words, translation
vs base, plurals without `other` - pure functions, so they're unit-tested on hand-made input),
`StringResourcesTest` and `NoNewLiteralsTest`. The baseline starts at **175 literals in 34 files** -
the regexes only match the parameters listed above, so it's well under the ~900 estimated for all
text; Step 4 should still grep each screen for literals the guard's patterns don't reach (e.g. list
items, `Text(buildString...)`) and widen the patterns when it finds a family. The Sora subset check
is unchanged until Step 2.

**Done when:** the four tests exist and pass, the baseline is checked in, and `.claude/I18N.md`'s
Status table is updated.

### Step 3 - Grammar helpers (done)

Can be done before or after Step 2, but not mixed into a Step 4 screen commit.

- Every remaining hand-rolled plural becomes a `<plurals>` entry: `GameScreen`'s timer,
  `StylesScreen`'s unlock counts, `LicensesDialog`'s `ComponentKind`, `AchievementAnnouncements`,
  `RulesScreen`'s "is/are locked". Find more with `grep -rn '== 1) "' app/shared/src/commonMain`.
- `grouped()` and `spokenList` become composables over `expect fun formatGrouped(n, languageTag)` /
  `formatList(items, languageTag)`, as Step 0 did for `ordinal` (see the table in Decisions), with
  a Robolectric check under `@Config(qualifiers = "fr")` that the output stays English (`34,521`,
  not `34 521`).
- Every sentence assembled from pieces becomes a whole-sentence template, with one template per
  variant where the shape changes (`targetProgress`'s four cases become four strings;
  `stackedSpokenState` becomes templates for the combinations it can produce - if that's more than
  about eight, stop and ask).

**What landed, and what was decided** (the user decided the first and last of these):

- **`grouped()`, `spokenList`, `joinClauses`, `joinSentences`** are composables in `ui/common/Formatting.kt`,
  over `expect fun formatGrouped` / `formatList` (`NumberFormat` / `ListFormatter` on Android,
  `NSNumberFormatter` / `NSListFormatter` on iOS), reading `common_locale`. `BoardSemanticsTest` checks
  `1,088` stays `1,088` under `@Config(qualifiers = "fr")`. The iOS actuals compile on Linux but have
  no `iosTest` and haven't run (Mac needed).
- **Sentences whose pieces come and go are built from clause strings, not enumerated** (about 48 combinations
  for `stackedSpokenState`, a similar spread for the Rules page's `spokenDescription`). Each clause is
  its own string; `common_clauses_join` / `common_sentences_join` (`"%1$s, %2$s"`, `"%1$s %2$s"`, folded
  pair by pair) join them, so a language can change the separator. This is the one place the "one
  sentence per string" convention is relaxed. Whitespace-only strings were avoided on purpose, since
  XML and Compose resources may trim them. Sentences with few variants (`targetProgress`, the styles banner)
  are whole-sentence templates.
- **Pluralised:** the turn timer, the styles banner's title, description and announcement, the styles
  requirement texts, the setup steppers (`ModifierStepper.valueText` replaced `unit`/`unitSingular`/
  `unitSeparator`; it's a composable lambda giving the whole phrase) and the Rules examples' "is/are
  locked" and "doesn't/don't count".
- **`ScoreGrid`'s inline tile sentences** ("Scored 12, plus 50 bonus", "Would score...") are still
  literals: they're Game screen text, and Step 4 reuses the `game_slots_*` clauses for them.
- **Left in English on purpose:** `LicenseGroup.usage` ("Used by 2 libraries"). The Android licence list
  is built from views that can't reach the resources, and one rarely-seen line isn't worth a new
  platform interface. Marked in its doc comment; revisit when a language is added.
- **Tests:** the styles banner and Third Wind sentence tests moved from `commonTest` to Robolectric
  (`StylesUnlockedBannerSemanticsTest`, `BoardSemanticsTest`); the visible banner text is read with
  `useUnmergedTree = true`.

### Step 4 - Screen-by-screen sweep (not started; needs Steps 1-3)

One commit per screen, under the existing categories. Each commit:

- moves the visible **and** spoken strings (`contentDescription`, `stateDescription`, action
  labels, live-region announcements) of that screen's files;
- keeps every string word for word the same - this is a move, not a rewrite;
- marks any literal that must stay with `// i18n: not translated - <why>`;
- lowers that screen's lines in the Step 1 baseline to 0 (or to the marked count);
- goes through `UI.md`'s accessibility checklist, with the report saying what TalkBack says before
  and after (it should be identical) and what wasn't heard on a device.

Model text on a screen (mode names, achievement titles) waits for Step 2; leave it and its baseline
count alone if Step 2 hasn't landed.

### Step 5 - Platform plumbing (deferred until a first language is added)

About an hour's work, done together with the first translation:

- **Android:** `androidResources { generateLocaleConfig = true }` in `app/android`, and
  `res/resources.properties` with `unqualifiedResLocale=en-GB`. This gives the per-app language
  picker on Android 13+. Translate `app_name` in `res/values-xx/strings.xml` if the name changes
  (it probably doesn't).
- **iOS:** `CFBundleLocalizations` in the app's Info.plist, or iOS won't offer the language; and an
  `InfoPlist.strings` per language for the display name. Belongs with `IOS_SUPPORT.md` Phase 5
  (needs macOS).
- **Dates:** `formatTimestamp` takes `common_locale`, like the other formatters.
- **Play Store:** a separate store listing per locale - add it to `PUBLISHING.md`. The store listing
  follows the same banned-words rule.
- **Sora:** if the language needs characters outside the subset, re-cut the font (the recipe is on
  `SoraFontFamily`) or fall back to the system font for that locale.
- **Testing:** run the Robolectric screen renders with the new locale (`@Config(qualifiers = "xx")`)
  to look for overflow; German-length strings are the usual problem.

### Adding a language after Step 5

1. Copy `values/strings.xml` to `values-xx/strings.xml` and translate it, supplying every plural
   form that CLDR gives the language, and setting `common_locale` to the language's tag.
2. Run the guards (banned words, title cap, Sora subset, missing keys).
3. Render the screens in that locale and check for overflow and truncation.
4. Do a TalkBack pass in that locale on a device.
5. Add the store listing.

## Effort

Steps 1-3: about two sessions. Step 4: two or three sessions of repetitive work. The APK size
change is negligible (one resource table; no new library).
